LIDR UDP protocol v1
====================

Transport:
  UDP -> Raspberry Pi 192.168.50.20:5005
  All integers and float32 values are little-endian.

Common header: 32 bytes
-----------------------
offset  size  field
0       4     magic = "LIDR"
4       1     version = 1
5       1     message type
6       2     header size = 32
8       4     message-specific id
12      2     message-specific field
14      2     message-specific field
16      2     message-specific field
18      2     message-specific field
20      8     ESP timestamp_us (esp_timer_get_time time base)
28      4     reserved = 0

Message type 1: POINT_CLOUD
---------------------------
Header fields:
8       4     frame_id
12      2     packet_id
14      2     packet_count
16      2     point_count in this datagram
18      2     total_point_count in whole frame

Point payload: 16 bytes per point
0       4     float32 x [m]
4       4     float32 y [m]
8       4     float32 z [m]
12      1     uint8 intensity
13      1     uint8 flags
              bit0 = stable temporal-history fill
              bit1 = historical point accumulated between current points
14      2     uint16 reserved = 0

Maximum 85 points/datagram:
32 + 85*16 = 1392-byte UDP payload.

Message type 2: IMU
-------------------
One UDP datagram per Unitree IMU MAVLink packet.

Header fields:
8       4     sample_id (monotonic counter generated by ESP)
12      2     Unitree source packet_id
14      2     0
16      2     IMU payload size = 40
18      2     0

IMU payload: 40 bytes
0       16    float32 quaternion[4]
16      12    float32 angular_velocity[3]
28      12    float32 linear_acceleration[3]

The IMU timestamp is captured with esp_timer_get_time() when the decoded
MAVLink IMU packet is received. Point-cloud frame timestamps use the same ESP
time base, so Raspberry can associate IMU samples with cloud frames.

Realtime behavior
-----------------
- UDP has no retransmission.
- Incomplete point-cloud frames are discarded on Raspberry after timeout.
- IMU packets are not retransmitted.
- Parser never blocks waiting for network transmission.

MESSAGE TYPE 3 - OBSTACLES
==========================
Generated from the final FUSED BUFFER 0 after temporal accumulation.

Header is unchanged (32 bytes):
- id_value             = source cloud frame_id
- field12              = obstacle packet_id
- field14              = obstacle packet_count
- field16              = obstacle_count in this datagram
- field18              = total obstacle count for frame
- timestamp_us         = source cloud timestamp

Obstacle record = 32 bytes, little-endian:
  float32 center_x
  float32 center_y
  float32 center_z
  float32 size_x
  float32 size_y
  float32 size_z
  float32 nearest_distance_m
  uint16  point_count
  uint16  flags

Up to 40 obstacle records are sent per datagram.  A frame with zero detected
obstacles still emits one 32-byte type-3 header so a receiver can clear stale
obstacles.
